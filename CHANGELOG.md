Next (V1.2.3)
---------------------

- Added the Dijkstra era (protocol version 12) serialization layer: CIP-118 nested transactions (`cardano_sub_transaction_body_t`, `cardano_sub_transaction_t`, `cardano_sub_transaction_set_t` and transaction body key 23), CIP-112 guards (`cardano_guard_set_t` at body key 14 with dual wire form, `cardano_required_guards_map_t` at key 24 on both body levels, the `RequireGuard` native script kind 6 and the `guarding` redeemer tag), direct deposits (key 25), account balance intervals (key 26), PlutusV4 serialization plumbing (script union tag 4, hash prefix 0x04, cost models key 3, auxiliary data key 5) and the four reference script protocol parameters (keys 34-37); a fresh parameter set leaves the reference script cost stride at 0 and the reference script cost multiplier unset (`cardano_protocol_parameters_get_ref_script_cost_multiplier` returns `NULL`), as the parameters of the eras before Dijkstra do not carry them, and the fee functions then price with the Conway values (25600 bytes, 6/5). The library stays era-less: decoders remain permissive for historical forms and encoders keep producing Conway-valid bytes unless a Dijkstra-only feature is used. Byte-exact round trips are pinned against the cardano-ledger golden vectors.
- Account balance intervals now support the exact balance form of the Dijkstra CDDL: `cardano_account_balance_interval_new_exact`, `cardano_account_balance_interval_get_exact_balance` and `cardano_account_balance_interval_is_exact` model an interval that requires an account balance to be exactly N lovelace, encoded on the wire as a bare unsigned integer instead of the two element bounds array. Range intervals keep their existing encoding.
- Added the Dijkstra protocol parameters 38 to 48 to `cardano_protocol_parameters_t` with getters and setters: `max_pledge_leverage` (CIP-50, nullable; `NULL` means unbounded and is the default), `min_pool_margin` (CIP-23) and the nine Leios parameters (CIP-164): `leios_announcement_period_length`, `leios_vote_period_length`, `leios_diffusion_period_length`, `leios_committee_size`, `leios_quorum_stake_threshold`, `max_endorser_block_references_size`, `max_endorser_block_txs_size`, `max_endorser_block_execution_units` and `max_ref_script_size_per_endorser_block`. Integer parameters are bounded to their wire width on set (16 bits for the committee size, 32 bits otherwise); a fresh parameter set defaults the new rationals to zero and the new execution units to (0, 0).
- Added `cardano_bls_key_t`, the optional BLS key (a 96 byte public key plus a 48 byte proof of possession) that Dijkstra stake pool registrations may carry for Leios voting. Pool parameters expose it through `cardano_pool_params_has_bls_key`, `cardano_pool_params_get_bls_key` and `cardano_pool_params_set_bls_key`, the pool registration certificate decodes both the 10 element (legacy) and the 11 element (with key) forms, and it keeps emitting the legacy form unless a key is set. The CIP-116 JSON of pool parameters gains a `bls_key` object only when a key is present.
- Account balance intervals maps are keyed by reward address (the serialized reward account bytes) as in the Dijkstra CDDL: `cardano_account_balance_intervals_map_t` maps each reward account to its interval. `get`, `insert`, `get_key_at` and `get_key_value_at` take and return `cardano_reward_address_t`, `get_keys` returns a `cardano_reward_address_list_t` in insertion order, and the new `cardano_account_balance_intervals_map_insert_ex` accepts a Bech32 reward address. The vendored Dijkstra golden transaction vector was re-pinned to the ledger commit that introduced this form.
- `cardano_protocol_param_update_t` now decodes, stores and re-encodes the same parameters 38 to 48 (CBOR keys, CIP-116 JSON with the snake_case names and the changed-parameters Plutus data map) so that Dijkstra parameter change proposals round trip and guardrail scripts see them. The pledge leverage update is nullable: `set_max_pledge_leverage` proposes a bound, `set_max_pledge_leverage_unbounded` proposes lifting it (CBOR null, JSON null, Plutus `Constr 1 []`), `clear_max_pledge_leverage` drops the key and `has_max_pledge_leverage` reports presence; the getter succeeds with a `NULL` interval for an unbounded proposal. Bounded integer parameters are validated to their wire width on decode and on set.
- Added the Dijkstra protocol parameters 49 to 56 (cardano-ledger `ef6c306e`) to `cardano_protocol_parameters_t` with getters and setters: the Peras parameters `peras_min_candidate_block_age`, `peras_healing_factor`, `peras_cert_boost`, `peras_target_committee_size`, `peras_bootstrap_round` (optional; `NULL` means no bootstrap round) and `peras_quorum_threshold_safety_margin`, and the reference input fee parameters `ref_inputs_cost_per_multi_asset_policy` and `ref_inputs_cost_per_datum_byte`. The ledger does not charge the reference input fees yet and the fee functions of the library ignore them.
- `cardano_protocol_param_update_t` now decodes, stores and re-encodes the parameters 49 to 56 (CBOR keys, CIP-116 JSON and the changed-parameters Plutus data map). The Peras bootstrap round update is nullable like the pledge leverage: `set_peras_bootstrap_round` proposes a round, `set_peras_bootstrap_round_null` proposes none (CBOR null, JSON null, Plutus `Constr 1 []`), `clear_peras_bootstrap_round` drops the key, `has_peras_bootstrap_round` reports presence and `is_peras_bootstrap_round_null` reports a proposal of no round. Unlike the pledge leverage getter, `get_peras_bootstrap_round` returns the round by value like every other integer parameter, and reports both an absent key and a null proposal as `CARDANO_ERROR_ELEMENT_NOT_FOUND`.
- Added `cardano_plutus_v4_script_set_t` and the Dijkstra witness set key 8 (`cardano_witness_set_get_plutus_v4_scripts` / `cardano_witness_set_set_plutus_v4_scripts`), so transactions and sub transactions that carry Plutus V4 scripts in their witness sets decode and round trip. V4 scripts in a witness set are found when resolving the scripts a transaction needs, and `cardano_witness_set_add_script` adds a V4 script to witness set key 8.
- Added the starting account balance intervals (transaction body key 27) to `cardano_transaction_body_t` through `cardano_transaction_body_get_starting_account_balance_intervals` and `cardano_transaction_body_set_starting_account_balance_intervals`. The field reuses `cardano_account_balance_intervals_map_t` and constrains, per reward account, the balance an account had before the batch started, while key 26 constrains the balance at the point the transaction is applied. It is encoded after key 26, only top level bodies carry it, and a sub transaction body that declares key 27 is rejected like the other top-level-only keys.
- The transaction decoder now preserves the Dijkstra 3-element frame (no `is_valid` flag) on re-encode; a transaction whose `is_valid` flag is false always serializes as the 4-element mempool frame so the flag is never lost. Witness sets preserve their decoded map key order for byte-exact round trips (fresh sets keep encoding canonically).
- **BREAKING (behavioral)**: `cardano_transaction_body_get_required_signers` now returns a derived, caller-owned view over the key-hash members of the body's guards (key 14 stores guards from this release); `set_required_signers` replaces the guards with key-hash credentials. Key-hash-only bodies keep serializing in the legacy Conway form. Multi-signer transactions built with `cardano_tx_builder_add_signer` now encode key 14 in insertion order instead of sorted order (wire-valid, but built transaction bytes can differ from prior releases), and adding a duplicate signer is now a no-op instead of emitting a duplicate entry.
- **BREAKING (behavioral)**: `cardano_transaction_body_from_cbor` now requires keys 0 (inputs), 1 (outputs) and 2 (fee), as the Conway and Dijkstra CDDL do, and returns `CARDANO_ERROR_DECODING` (with the reader's last error set) when any of them is absent; `cardano_transaction_from_cbor` propagates the same error for such bodies. Bodies such as `a0` or a fee-only map, which previously decoded, are now rejected. An empty outputs list under key 1 is still accepted, and encoding is unchanged.
- Wire tightenings per the Dijkstra CDDL: bootstrap witness chain codes must be exactly 32 bytes, protocol version minor is bounded to uint32, redeemer indices are bounded to uint32 on fresh encodes, empty multiasset maps and empty policy maps are never emitted (values collapse to plain coin), and cost model arrays decode in indefinite-length form.
- Added `cardano_random_improve_coin_selector_new` (and `_new_with_seed` for deterministic behavior): a Round-Robin Random-Improve coin selector ported from cardano-wallet's coin selection algorithm. It selects UTxOs at random per required asset in round-robin order, improving each selection toward twice the minimum, and generates one min-ADA compliant change output per user-specified output, with change sized to mimic the user's payments. The selector RNG is re-seeded on every selection so that repeated invocations from the balancing loop are reproducible.
- **BREAKING**: `cardano_coin_selector_select` and the `cardano_coin_select_func_t` callback now receive all selection inputs through a single `cardano_coin_selection_request_t` structure (pre-selected UTxOs, available UTxOs, the authoritative target, an optional `outputs_to_cover` shape hint for change generation, the change address and the protocol parameters). Future request fields will be appended with zero-value defaults, so this is intended to be the last signature change to the selector interface.
- **BREAKING**: Refactored coin selection to support multiple change outputs (in preparation for Round-Robin Random-Improve). `cardano_coin_selector_select` and the `cardano_coin_select_func_t` callback now take the change address and the protocol parameters, and return the change outputs explicitly through a new `cardano_transaction_output_list_t** change_outputs` out parameter. Selectors are now responsible for producing locally balanced (`sum(selection) = target + sum(change_outputs)`), min-ADA compliant change outputs; the balancer keeps full responsibility for fee convergence, implicit coin accounting and the final transaction balance check. The min-ADA padding retry loop was removed from the balancer accordingly.
- Added deferred redeemer callbacks (`cardano_deferred_redeemer_fn_t`): `cardano_tx_builder_add_input_with_deferred_redeemer`, `cardano_tx_builder_mint_token_with_deferred_redeemer`, `cardano_tx_builder_withdraw_rewards_with_deferred_redeemer`, `cardano_tx_builder_add_certificate_with_deferred_redeemer` and `cardano_tx_builder_vote_with_deferred_redeemer` register a callback that builds the redeemer payload from the balanced draft transaction, once the final canonical input order, change outputs and fee are known. Callbacks run on every balancing iteration and must be pure. This enables redeemers that carry script-context indices (witness-driven design patterns), for every redeemer purpose the builder can attach: spends, mints, withdrawals, certificates and votes.
- Added canonical index lookup helpers on transactions: `cardano_transaction_find_input_index`, `find_reference_input_index`, `find_output_index`, `find_mint_policy_index`, `find_withdrawal_index`, `find_certificate_index`, `find_vote_index` and `find_redeemer_index`.
- **BREAKING**: `cardano_balance_transaction` takes an additional (nullable) `cardano_deferred_redeemer_list_t*` parameter.
- Added `cardano_random_improve_coin_selector_new_with_options` and `cardano_selection_strategy_t`: the random improve selector can now use the "minimal" selection strategy (select just enough of each asset) in addition to the default "optimal" strategy (improve toward twice the minimum).
- **BREAKING (behavioral)**: The transaction builder now uses the Round-Robin Random-Improve selector by default instead of the large-first selector. Use `cardano_tx_builder_set_coin_selector` with `cardano_large_first_coin_selector_new` to restore the previous behavior.
- Coin selectors now split change outputs whose assets would exceed the protocol's maximum output value size (`max_value_size`): oversized change bundles are recursively halved until every change output fits, for both the large-first and the random-improve selectors. A `max_value_size` of zero disables the check.
- Added property-based tests for coin selection (ported from the cardano-js-sdk input-selection property tests): generative scenarios validate coverage, local balance, min-ADA compliance of change outputs, UTxO conservation and honest failure reporting against an independent integer-arithmetic oracle.
- Added `cardano_tx_builder_add_guard` and `cardano_tx_builder_add_guard_ex` to the transaction builder: they add an arbitrary CIP-112 guard credential to the transaction body. A key hash guard is a required signer and produces the same transaction as `cardano_tx_builder_add_signer`; a script hash guard requires the ledger to run the script with the guarding redeemer purpose and switches body key 14 to the Dijkstra credential wire form. Duplicate guards are ignored and the builder does not attach the guard script or its redeemer.
- Added transaction imbalance helpers to the balancing module: `cardano_compute_transaction_imbalance` and `cardano_compute_sub_transaction_imbalance` return the value a transaction or a CIP-118 sub transaction consumes minus the value it produces (resolved inputs, withdrawals, deposit refunds and minted assets against outputs, fee, deposits, donation, direct deposits and burned assets) as a signed `cardano_value_t`, so that parties can hand-assemble sub transactions and batchers can match their intents. `cardano_compute_sub_transaction_implicit_coin` reports the withdrawals, deposits and refunds of a sub transaction body. `cardano_is_transaction_balanced` is now computed from the imbalance (a zero batch imbalance, see `cardano_compute_transaction_batch_imbalance` below) and therefore accounts for direct deposits (body key 25) as produced value.
- Added direct deposit and account balance interval setters to the transaction builder: `cardano_tx_builder_add_direct_deposit` and `cardano_tx_builder_add_direct_deposit_ex` pay lovelace straight into a reward account without creating a UTxO (body key 25), `cardano_tx_builder_add_account_balance_interval` and `cardano_tx_builder_add_account_balance_interval_ex` make the transaction valid only while a reward account balance sits inside an interval (key 26), and `cardano_tx_builder_add_starting_account_balance_interval` and `cardano_tx_builder_add_starting_account_balance_interval_ex` assert the balance an account had before any sub transaction was applied (key 27). Direct deposits to the same reward account accumulate (an amount or an accumulated amount above `INT64_MAX` is reported as `CARDANO_ERROR_INTEGER_OVERFLOW` and a zero amount is rejected), while a new interval replaces the previous one of the same account. `cardano_balance_transaction` now funds direct deposits from the selected inputs together with the outputs and the fee. This change does not alter the bytes of transactions that carry no direct deposits and no account balance intervals.
- Added `cardano_compute_transaction_batch_imbalance` to the balancing module: it returns the imbalance of a whole CIP-118 batch, the imbalance of the top level transaction body plus the imbalance of every sub transaction it carries (coin and multi assets), which is the figure the ledger checks for value conservation. The resolved inputs must cover the top level body and every sub transaction. `cardano_is_transaction_balanced` is now defined as a zero batch imbalance, so it gives the whole batch answer for a transaction that carries sub transactions; `cardano_compute_transaction_imbalance` still reports the top level body alone, and this change does not alter the results for transactions without sub transactions.
- Added `cardano_sub_tx_builder_t`, a dedicated builder for CIP-118 sub transactions that produces a `cardano_sub_transaction_t` through `cardano_sub_tx_builder_build`. A sub transaction is an intent, so the builder never balances: it performs no coin selection and adds no change, fee or collateral, the result spends exactly the inputs and produces exactly the outputs that were added, and its imbalance (`cardano_compute_sub_transaction_imbalance`) is what a batcher matches against the rest of the batch. Because it is a separate type, the fields that only exist on a top level transaction (fee, collateral, starting account balance intervals) have no functions on it. The core surface mirrors the transaction builder: `cardano_sub_tx_builder_new`, `_ref`, `_unref`, `_refcount`, `_set_last_error`, `_get_last_error`, `_set_network_id`, `_set_donation`, `_set_invalid_after`, `_set_invalid_after_ex`, `_set_invalid_before`, `_set_invalid_before_ex`, `_add_input`, `_add_reference_input`, `_add_output`, `_send_lovelace`, `_send_lovelace_ex`, `_send_value`, `_send_value_ex`, `_set_metadata`, `_set_metadata_ex`, `_mint_token`, `_mint_token_ex`, `_mint_token_with_id`, `_mint_token_with_id_ex`, `_add_script`, `_add_signer`, `_add_signer_ex`, `_add_guard`, `_add_guard_ex`, `_add_direct_deposit`, `_add_direct_deposit_ex`, `_add_account_balance_interval` and `_add_account_balance_interval_ex`. `cardano_sub_tx_builder_add_input` takes the same optional redeemer and datum as `cardano_tx_builder_add_input`, so a party can spend an input locked by a PlutusV4 script: the index of the spend redeemer is set from the position of the input in the sorted inputs of the sub transaction when it is built, and its execution units are computed with the native evaluator, while an input locked by a PlutusV1, PlutusV2 or PlutusV3 script makes `cardano_sub_tx_builder_build` return `CARDANO_ERROR_INVALID_SCRIPT_LANGUAGE`, and it returns `CARDANO_ERROR_ELEMENT_NOT_FOUND` for a datum hash locked input whose datum was not provided. `cardano_sub_tx_builder_require_top_level_guard` and `cardano_sub_tx_builder_require_top_level_guard_ex` require a guard credential, with an optional datum, from the top level transaction that carries the sub transaction (body key 24). PlutusV1, PlutusV2 and PlutusV3 scripts can not run inside a sub transaction, so `cardano_sub_tx_builder_add_script` reports them as `CARDANO_ERROR_INVALID_SCRIPT_LANGUAGE` when building; native and PlutusV4 scripts are accepted. `cardano_sub_tx_builder_add_direct_deposit` and `cardano_sub_tx_builder_add_direct_deposit_ex` follow the rules of the transaction builder functions: a zero amount is rejected, and an amount, or an accumulated amount for the same reward account, above `INT64_MAX` is reported by `cardano_sub_tx_builder_build` as `CARDANO_ERROR_INTEGER_OVERFLOW`, leaving the direct deposits already added unchanged. `cardano_sub_tx_builder_add_signer` and `cardano_sub_tx_builder_add_signer_ex` add a required signer, which is a key hash guard, so they produce the same sub transaction as `cardano_sub_tx_builder_add_guard` with a key hash credential; there is no `pad_signer_count` because a sub transaction pays no fee.
- Added certificates, withdrawals, votes and governance proposals to `cardano_sub_tx_builder_t`, so a party of a CIP-118 batch can express those intents in a sub transaction whose fee is paid by the batcher: `cardano_sub_tx_builder_withdraw_rewards`, `_register_reward_address`, `_deregister_reward_address`, `_delegate_stake`, `_delegate_voting_power`, `_register_drep`, `_update_drep`, `_deregister_drep`, `_propose_parameter_change`, `_propose_hardfork`, `_propose_treasury_withdrawals`, `_propose_no_confidence`, `_propose_update_committee`, `_propose_new_constitution` and `_propose_info`, each with its `_ex` variant that takes strings, plus `cardano_sub_tx_builder_vote` and `cardano_sub_tx_builder_add_certificate`. These and the minting functions mirror the signatures of the transaction builder functions, including the optional redeemer where the transaction builder function takes one, so a party can mint with a PlutusV4 policy (`cardano_sub_tx_builder_mint_token` and its variants), withdraw from a PlutusV4 script account, publish certificates of a PlutusV4 script credential, vote as a PlutusV4 script voter and make parameter change and treasury withdrawals proposals validated by a PlutusV4 guardrails script inside its sub transaction. The indices of those redeemers are local to the body of the sub transaction and their execution units are computed with the native evaluator when `cardano_sub_tx_builder_build` is called, while a PlutusV1, PlutusV2 or PlutusV3 policy, account, voter or guardrails script makes it return `CARDANO_ERROR_INVALID_SCRIPT_LANGUAGE`. Key and native script credentials take a NULL redeemer. Redeemers whose payload depends on the final shape of the sub transaction are added through `cardano_sub_tx_builder_add_input_with_deferred_redeemer`, `_mint_token_with_deferred_redeemer`, `_withdraw_rewards_with_deferred_redeemer`, `_add_certificate_with_deferred_redeemer` and `_vote_with_deferred_redeemer`, which mirror the deferred redeemer functions of the transaction builder. Their callbacks run when `cardano_sub_tx_builder_build` is called, after the spend redeemer indices are set and before evaluation, and receive a transaction that carries the sorted inputs, the outputs and every other field of the sub transaction body together with the spent UTXOs in that same order, so an index a callback computes, such as the position of an input or an output, is local to the body that is signed, and the produced payloads are evaluated and covered by the script data hash. A failing callback makes `cardano_sub_tx_builder_build` return the error of the callback. Withdrawals and deposit refunds count as value consumed and certificate and proposal deposits as value produced in `cardano_compute_sub_transaction_imbalance`. The documentation of `cardano_tx_builder_withdraw_rewards` and `cardano_tx_builder_withdraw_rewards_ex` now describes the Dijkstra withdrawal rules: partial withdrawals are valid as long as the withdrawals of an account over the whole batch do not exceed its balance before the batch, while a top level transaction that needs a PlutusV1, PlutusV2 or PlutusV3 script must still drain the account exactly.
- Added `cardano_sub_tx_builder_lock_lovelace`, `cardano_sub_tx_builder_lock_lovelace_ex`, `cardano_sub_tx_builder_lock_value`, `cardano_sub_tx_builder_lock_value_ex` and `cardano_sub_tx_builder_add_datum` to the sub transaction builder, with the same semantics as their `cardano_tx_builder_*` counterparts: a party of a CIP-118 batch can lock lovelace or a value at a script address with an inline datum or a datum hash, and attach a supplemental datum. The datums added to a sub transaction are carried in the plutus data of its witness set and are covered by its script data hash.
- Added `cardano_tx_builder_add_sub_transaction` to the transaction builder, the batcher side of CIP-118: it adds a finished sub transaction to the sub transaction set of the transaction body (key 23) together with the UTXOs that resolve its inputs. The sub transaction is opaque, the builder keeps a reference to it and never modifies it, so its original bytes, its id and its signatures are preserved. A sub transaction whose id is already in the batch, that spends an input already spent by another sub transaction or by an input added with `cardano_tx_builder_add_input`, or whose spend inputs are not all resolved is rejected with a deferred error, and `cardano_tx_builder_add_input` now rejects an input that is already spent by a sub transaction. The fee prices the reference scripts carried by the UTXOs the sub transaction spends, and the resolved UTXOs may also resolve the reference inputs of the sub transaction, whose reference scripts are then priced too. The batcher must add every top level guard a sub transaction requires with `cardano_tx_builder_add_guard`: the builder never adds them by itself and `cardano_tx_builder_build` fails with `CARDANO_ERROR_ELEMENT_NOT_FOUND` when one is missing.
- `cardano_balance_transaction` and `cardano_tx_builder_build` now balance whole CIP-118 batches, as the ledger checks value conservation over the top level transaction together with its sub transactions: the net imbalance of the sub transactions is part of the value coin selection must cover, so a net deficit is funded by additional top level inputs and a net surplus is returned in the change outputs, for lovelace and for every asset. The signature of `cardano_balance_transaction` does not change for this: the resolved UTXOs of the sub transactions, the ones they spend and optionally the ones they reference, are given in `available_utxo` next to the UTXOs the top level transaction may spend, and `cardano_tx_builder_build` adds there the UTXOs of the sub transactions, the ones they spend or reference, that were given to `cardano_tx_builder_add_sub_transaction`, without listing twice a UTXO that is already among the available ones. The role of each UTXO is taken from the bodies of the sub transactions: a UTXO that a sub transaction spends or references is never selected as a top level input nor used as collateral, even when it is also among `available_collateral_utxo` because the batcher is a party of the batch, and an input of a sub transaction is looked up in `available_utxo` first, then in `reference_inputs` and then in `pre_selected_utxo`, since a UTXO may be shared between the top level transaction and a sub transaction. When collateral is required and every UTXO of `available_collateral_utxo` is used by a sub transaction, balancing fails with `CARDANO_ERROR_BALANCE_INSUFFICIENT`. A sub transaction spend input that none of those lists resolves is reported with `CARDANO_ERROR_ELEMENT_NOT_FOUND`, a pre selected UTXO that a sub transaction also spends is rejected with `CARDANO_ERROR_DUPLICATED_KEY`, and the result is verified with the whole batch balance check. `reference_inputs` keeps holding the resolved reference inputs of the top level transaction only. The UTXOs that only sub transactions use are handed to the transaction evaluator together with the ones of the top level transaction, so that it can resolve every level of the batch, and the scripts the sub transactions need never make the top level transaction conserve value by itself. When the top level transaction needs a PlutusV1, PlutusV2 or PlutusV3 script, that is when a script of one of those languages runs because the transaction spends an input it locks, mints under its policy, withdraws from a reward account it controls, carries a certificate it must authorize, votes with it as the voter, carries a parameter change or treasury withdrawals proposal it guards as the guardrails script or lists it among its guards, whatever source of the batch provides the script (the witness set of the top level transaction or of one of its sub transactions, or a reference script of a resolved reference input or spent input of any level, including the inputs chosen by coin selection, as the ledger pools the provided scripts over the whole batch; a reference input of a sub transaction whose UTXO the balancer is not given is not seen), the ledger also requires it to balance by itself, so sub transactions that do not balance between themselves are reported with the new `CARDANO_ERROR_UNBALANCED_SUB_TRANSACTIONS` error code; the fix is to add a balancing sub transaction. A script that is only present and that the transaction does not need, and a needed native or PlutusV4 script, do not trigger this rule. In that same legacy mode the ledger checks the witness datums of the top level transaction with its sub transactions removed, so a top level datum that is neither needed by an input it spends that a Plutus script among the pooled scripts locks (an input locked by a native script, or by a script that nothing provides, never needs its datum, even when it carries a datum hash) nor matches the datum hash of one of its own outputs or of the output behind one of its own reference inputs, for example a datum whose hash only an output of a sub transaction carries, is reported with the new `CARDANO_ERROR_NOT_ALLOWED_SUPPLEMENTAL_DATUMS` error code. This change does not alter how transactions without sub transactions are balanced.
- Fees and collateral are now computed for whole CIP-118 batches, since the top level transaction pays for its sub transactions. `cardano_compute_min_script_fee` and `cardano_compute_transaction_fee` add the execution units of the redeemers of every sub transaction (body key 23) to the ones of the top level witness set before pricing them, and the reference script fee counts every entry of the resolved UTXOs it is given, so a UTXO referenced by the transaction and by a sub transaction is priced once per body, as the ledger measures the reference script size of a batch. The reference scripts of the sub transactions are included and the size of the whole batch is priced with a single application of the tiered model, as the ledger does since `getDijkstraMinFeeTxUtxo`. `cardano_balance_transaction` and `cardano_tx_builder_build` pay for the execution units of the sub transactions, include the reference scripts of their resolved reference inputs and of the UTXOs they spend (taken from the body of each sub transaction and resolved from the UTXOs given to the balancer, so a UTXO that a sub transaction both references and spends is priced once, a UTXO referenced by several sub transactions is priced once per sub transaction, and a reference input of a sub transaction that is not resolved is not priced), and add collateral when a redeemer exists anywhere in the batch, still sized from the fee of the top level transaction with the collateral percentage. The execution units the redeemers of sub transactions declare are taken as final, since they are signed by the party that built each sub transaction. When the top level transaction carries redeemers, the transaction evaluator runs the scripts of every level together, as the ledger does, so a sub transaction script that fails makes balancing and building fail. `cardano_tx_builder_build` requires the collateral change address and the collateral UTXOs when only a sub transaction carries redeemers, and reports their absence with the same errors as for a top level script. This change does not alter the fees and collateral of transactions without sub transactions.
- Added `cardano_sub_transaction_apply_vkey_witnesses`, the counterpart of `cardano_transaction_apply_vkey_witnesses` for CIP-118 sub transactions: it adds the vkey witnesses of the party that signed the sub transaction id to the witness set of the sub transaction. The body is never touched, so the id and the signed bytes are preserved.
- Added the `sub_transaction_batch_example` example and an end to end settlement test suite for CIP-118 batches: two parties express opposite intents as signed sub transactions and a batcher aggregates and balances them. The example runs offline with hardcoded UTXOs, its parties and its batcher sign through software secure key handlers, and it prints the CBOR of the batch. The tests cover a batch that nets to zero, a deficit funded by the batcher, a surplus kept by the batcher as change and an intent handed over as bytes that carries a direct deposit, a stake registration and a withdrawal, check that the embedded sub transactions stay byte identical and their signatures keep verifying, and include a property test over random sets of sub transactions with random ADA and token imbalances.

A `constr` or `case` term in a program of Plutus Core version below 1.1.0 is rejected, a constant of a BLS12-381 type has no flat form and is rejected, a program with bytes left over after its final filler is rejected, and `array` and `value` constants are decoded (a `value` must be canonical) and encoded. As a result `cardano_uplc_apply_params_to_script` returns `CARDANO_ERROR_DECODING` for a script with a BLS12-381 constant, with a `constr` or `case` term in a 1.0.0 program or with bytes after the flat program, and accepts scripts with `array` and `value` constants.
- The native transaction evaluator (`cardano_tx_evaluator_new_native`) now follows the ledger tables for which languages and builtins are available at each protocol version: Plutus V1 from protocol version 5, V2 from 7, V3 from 9 and V4 from 12, and each builtin from the release batch that introduced it. A script in a language that is not available yet, or that names a builtin that is not available yet, cannot be deserialised and is reported as `CARDANO_ERROR_DECODING`. Deserialising a script also rejects a constant type header longer than 32 type tags and a `constr` term with more than 1024 fields. Like the ledger, bytes after the CBOR byte string of a Plutus V1 or V2 script are now ignored, where they made the script undecodable before; after a V3 or V4 script they are still rejected.
- The native transaction evaluator now checks the Plutus Core version of a script against the protocol version: version 1.1.0 is available to Plutus V1 and V2 scripts only from protocol version 11 (to V3 once V3 is available) and version 1.2.0 only from protocol version 12. A script of an unavailable version is reported as a phase-2 failure, `CARDANO_ERROR_SCRIPT_EVALUATION_FAILURE`, without running the machine.
- Fixed the native transaction evaluator (`cardano_tx_evaluator_new_native`) accepting `case` on a constant of a built-in type before protocol version 11. Like the ledger, it now fails the script.
- The native transaction evaluator now runs Plutus V4 scripts from protocol version 12, priced by the V4 cost model of the protocol parameters, found in the witness set (key 8) or as reference scripts. A V4 script receives the V4 script context and succeeds only when it returns unit. It also runs the guarding redeemers (tag 6), whose index is the position of the script hash guard in the guard set (body key 14), counting key hash guards, and the scripts of sub transactions: a transaction and its sub transactions are evaluated together, as the ledger does, every script of every level is deserialised before any of them runs, the redeemers of a sub transaction come from its own witness set and get the script context of that sub transaction, and a script of any level can be provided by the witness set of any level. A sub transaction redeemer that runs a V1, V2 or V3 script is reported as `CARDANO_ERROR_INVALID_SCRIPT_LANGUAGE`. `cardano_tx_evaluator_new_native` keeps returning the redeemers of the top level transaction, and the new `cardano_tx_evaluator_new_native_sub_transaction` creates an evaluator that returns the redeemers of the sub transaction at a given position. A cost model set that has no entry for the language of a script now falls back to the default cost model instead of failing with `CARDANO_ERROR_POINTER_IS_NULL`.
- Added `cardano_tx_builder_add_guard_with_redeemer` and `cardano_sub_tx_builder_add_guard_with_redeemer`: they add a script hash guard together with the guarding redeemer that satisfies it, at the position of the guard in the guard set. The sub transaction builder now evaluates the redeemers of the sub transaction with the native evaluator when building, so the sub transaction carries its final execution units and script data hash before it is signed; a script that fails is reported as `CARDANO_ERROR_SCRIPT_EVALUATION_FAILURE`. The sub transaction is evaluated at position 0 of a batch that holds nothing else, and its script context carries its position in the batch, so a script whose path or cost depends on that position may need different execution units in the final batch. `cardano_balance_transaction` and `cardano_tx_builder_build` now forward the inputs and reference inputs of the sub transactions to the evaluator, so it can resolve every level of the batch. The builders include the PlutusV4 cost model in the script data hash when the transaction needs a PlutusV4 script, as they do for the other Plutus languages. Added the `plutus_v4_guarded_sub_transaction_example` example: it spends from a Plutus V4 validator in a transaction that carries a sub transaction guarded by a Plutus V4 script, built offline for a Dijkstra network.
- Fixed `cardano_transaction_body_new` leaving the output pointer set to the released body when it runs out of memory, so a caller that released it on failure released it twice. It now sets the output pointer to `NULL` on failure.
- Fixed `cardano_tx_evaluator_new_native` reading past the end of the evaluator name while copying it.
- Fixed the native transaction evaluator (`cardano_tx_evaluator_new_native`) accepting a Plutus V3 script that returns a value other than unit. Like the ledger, a V3 or V4 script now succeeds only when it returns unit and any other result is reported as `CARDANO_ERROR_SCRIPT_EVALUATION_FAILURE`; V1 and V2 scripts may still return any value.
- The native transaction evaluator now rejects a Plutus V1, V2 or V3 script in a transaction that carries direct deposits (body key 25), account balance intervals (key 26), required top level guards (key 24) or a script hash credential among its guards (key 14), as the ledger does since their script context cannot represent those fields. Such a transaction is reported as `CARDANO_ERROR_INVALID_ARGUMENT`, as a V1 or V2 script already was in a transaction with votes, proposals, a current treasury value or a treasury donation. Key hash guards are still accepted, and Plutus V4 scripts are not affected.
- Fixed the native transaction evaluator (`cardano_tx_evaluator_new_native`) building Plutus V1, V2 and V3 script contexts whose maps and lists were not in the order the ledger uses, so a script could see a different context than on chain and succeed, fail or cost differently. Asset names in every value and mint now sort byte by byte instead of shortest first; witness datums sort by hash instead of witness order, a repeated datum appears once, and the V1 datum field is a list of (hash, datum) pairs instead of a map; V3 withdrawals and the withdrawals of a treasury withdrawals proposal put script credentials before key credentials; V3 votes list committee members, then DReps, then stake pools, each with script credentials first; the members an UpdateCommittee proposal removes and adds put script credentials first; the quorum of an UpdateCommittee proposal is reduced to lowest terms; and a V3 output with a zero ada amount keeps its ada entry. V1 and V2 withdrawals keep listing key credentials first, as the Plutus V1 and V2 types order them.
- Fixed the native transaction evaluator resolving a reward or voting redeemer to the wrong withdrawal or voter when key and script credentials are mixed. The ledger counts the index of a reward redeemer over the withdrawals with script credentials first and the index of a voting redeemer over the voters with script credentials first within each role, while the evaluator used the order of the library maps, which put key credentials first. It could then run the wrong script, give a script the purpose of another credential, or report `CARDANO_ERROR_INVALID_ARGUMENT` for a valid transaction.
- Fixed `cardano_tx_builder_vote` and `cardano_tx_builder_vote_with_deferred_redeemer` assigning voting redeemer indices with key credential voters before script credential voters of the same role. When a committee member or DRep voted with a script next to a key voter of the same role, the voting redeemer pointed at the wrong voter and the ledger rejected the transaction. Indices now follow the ledger voter order.
- Fixed `cardano_transaction_find_withdrawal_index` and `cardano_transaction_find_vote_index` returning the position of a withdrawal or voter in the library maps, which put key credentials first, instead of the index reward and voting redeemers use. They now count in ledger order: withdrawals by network, then script credentials before key credentials, then hash; voters by role, then script credentials before key credentials, then hash. `cardano_transaction_find_withdrawal_index` no longer allocates.
- Fixed `cardano_datum_get_data_hash`, `cardano_datum_get_data_hash_bytes` and `cardano_datum_get_data_hash_hex` returning a zero or garbage hash for an inline datum, so funds locked with that hash could not be spent. For an inline datum they now return the datum hash of its plutus data, the blake2b-256 hash of its CBOR encoding, computed from the data on every call; plutus data decoded from CBOR is hashed over the bytes it was decoded from (until its CBOR cache is cleared), so the hash matches the one the ledger computes. `cardano_datum_get_data_hash_hex_size` reports the size of that hex string, and `cardano_datum_get_data_hash_bytes` and `cardano_datum_get_data_hash_hex` return `NULL` when the hash of an inline datum cannot be computed. Datums created from a hash behave as before.
